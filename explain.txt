1. WHAT THIS PLATFORM DOES
--------------------------------------------------------------------------------
A web app for a small/medium NGO to run fundraising and volunteering:

  • Manage donors, campaigns (fundraisers) and donations — including taking
    real online payments through Razorpay.
  • Manage volunteers, volunteer shifts, and events (with registrations and
    paid tickets).
  • Give donors and volunteers their own accounts, dashboards and self-service
    pages (their donations, active campaigns, edit-profile, PDF export).
  • Give staff/superusers analytics (total raised, monthly trend, campaign
    progress) and an easy CSV export of a month's donations.

Stack:
  • Backend: Django 5.x — four apps: `core`, `payments`, `reports`, `api`.
  • Frontend: React 18 + Vite (dev server on :5173, proxying /api → Django :8000).
  • Database: Postgres via Supabase (SQLite works too — see §20).
  • Payments: Razorpay Standard Checkout (test mode with test keys).

2. RUNNING IT LOCALLY
--------------------------------------------------------------------------------
Backend (terminal A):
    cd C:\Users\GARVIT\ngo_platform
    python manage.py runserver 0.0.0.0:8000
    # Django serves the JSON API at /api/* and the admin at /admin

Frontend (terminal B):
    cd C:\Users\GARVIT\ngo_platform\frontend
    npm install              # (if NODE_ENV=production is set, use: npm install --include=dev)
    npm run dev              # Vite dev server on http://localhost:5173

Open http://localhost:5173 in a browser. The Vite proxy forwards /api requests
to Django (http://127.0.0.1:8000), so cookies and CSRF just work same-origin.

Environment (.env at the project root — gitignored):
    DJANGO_SECRET_KEY, DJANGO_DEBUG, DJANGO_ALLOWED_HOSTS
    RAZORPAY_KEY_ID, RAZORPAY_KEY_SECRET, RAZORPAY_WEBHOOK_SECRET
    DJANGO_DB_ENGINE/NAME/USER/PASSWORD/HOST/PORT (+ SSLMODE)
    DONATION_CURRENCY, DONATION_ACK_FROM_EMAIL, DJANGO_TIME_ZONE

IMPORTANT: If RAZORPAY_KEY_ID/RAZORPAY_KEY_SECRET are missing or blanked out,
online payments turn OFF and the app silently records donations as offline/cash
(that is deliberate — see §8). To enable online donations, generate test keys in
the Razorpay Dashboard (Settings → API Keys), paste them into .env, restart
Django. The webhook secret is separate and only needed if you wire the real
Razorpay webhook (see §9).

3. PROJECT LAYOUT & ARCHITECTURE
--------------------------------------------------------------------------------
ngo_platform/
├─ apps/
│  ├─ core/        # domain models + CRUD views + business services
│  ├─ payments/    # Razorpay order creation, signature verify, webhook processing
│  ├─ reports/     # dashboard aggregation + monthly CSV export
│  └─ api/         # auth, /auth/me, /me/* self-service endpoints, user mgmt
├─ frontend/src/
│  ├─ pages/       # one file per screen (Dashboard, DonorDashboard, MyDonations…)
│  ├─ components/  # Layout, StatCard, Avatar, StatusBadge, Toasts, modals…
│  ├─ hooks/       # useData, useDonate, useClientFilter
│  ├─ lib/         # format.js (INR/date), exportPdf.js, razorpay.js (checkout)
│  ├─ auth/        # AuthContext + ProtectedRoute
│  └─ App.jsx      # all routes
├─ ngo_platform/   # Django settings, root urls, wsgi/asgi
├─ .env            # real secrets (gitignored) — never commit
└─ explain.txt     # this file

Django "app package" gotcha: apps/ is added to sys.path, so imports use the
top-level name — `from core.models import Donation`, NOT `from apps.core.models
import ...`. The latter creates a phantom second module and raises
"Model class apps.core.models.X doesn't declare an explicit app_label".
When in doubt, always import as `core.*`, `payments.*`, `reports.*`, `api.*`.

How a browser request becomes JSON:

    React <form/button>
      → api.js fetch('/api/...')            (same-origin via Vite proxy)
      → Django urls.py → view → JsonResponse
      → React reads data, renders

Auth wire-up: Django session cookies. fetch() sends the session cookie
automatically (credentials: 'include'); every write request also echoes the
`csrftoken` cookie back in the `X-CSRFToken` header (see frontend/src/api.js).
The login and /me views set the CSRF cookie via ensure_csrf_cookie.

4. THE DATA MODEL (EVERY MODEL, AT A GLANCE)
--------------------------------------------------------------------------------
All models are in apps/core/models.py (except the two payment-audit models below).

  Tag                 free-form donor label ("monthly", "corporate"…), M2M → Donor.
  Donor               person/org giving money. donor_type = individual|organization.
                      Optional OneToOne link to a User (self-service donors).
                      merged_into + is_active support dedup (soft delete).
                      total_given property = sum of captured+succeeded+paid donations.
  DonorCommunication  audit log of outbound email/SMS/letter to a donor.
  Campaign            a fundraiser. status draft|active|completed|cancelled.
                      goal_amount (0 = "no goal"). raised_amount and
                      progress_percent are PROPERTIES computed from its donations.
  Donation            one gift. status mirrors the Razorpay lifecycle (see §9):
                      initiated → order_created → payment_pending → captured/
                      succeeded, or failed, part_refunded, refunded.
                      frequency once|monthly|quarterly|annual.
                      auto receipt_number stamp ACK-YYMM-millis.
                      razorpay_order_id / payment_id / signature / link_id /
                      refund_amount, acknowledgement_sent_at.
  Volunteer           volunteer profile. background_check_status =
                      not_required|pending|cleared|rejected. total_hours property.
                      Optional OneToOne link to a User.
  VolunteerShift      a shift (title, times, capacity, status
                      draft|open|locked|cancelled|completed).
  ShiftSignup         volunteer ↔ shift (unique per pair). status signed_up|
                      confirmed|waitlisted|checked_in|checked_out|no_show|cancelled.
                      hours_logged feeds total_hours.
  Event               a fundraiser event. capacity (0 = unlimited), ticket_price
                      (0 = free). Optional FK → Campaign so event revenue rolls
                      into the campaign total. status draft|published|cancelled|completed.
                      registrations_count, revenue = properties.
  EventRegistration   a ticket. donor OR volunteer FK (either kind of person may
                      attend). status pending|confirmed|attended|waitlisted|cancelled.
                      paid_amount only counts when confirmed/attended.
  UserProfile         the ROLE of a self-service account: volunteer|donor.
                      Staff/superusers have NO UserProfile (they're identified by
                      Django's is_staff / is_superuser flags).
  RazorpayWebhookEvent (payments app) — immutable audit log of every webhook
                      delivered by Razorpay. status received|processed|duplicate|failed|signature_invalid.
  PaymentLink         (payments app) — created Payment Links for sharing with donors.

Amounts are stored as INR decimals and converted to PAISE (×100) only at the
Razorpay boundary (§7, §9). Campaign/progress math coerces goal and raised to
Decimal so a string value never 500s the divide.

5. ACCOUNTS, ROLES & PERMISSIONS
--------------------------------------------------------------------------------
Three kinds of people use the app:

  • Anonymous visitors — can READ public lists (donors, donations, campaigns,
    volunteers, events) via the JSON API; cannot write anything.
  • Registered end-users (self-service signup) — have a UserProfile role:
       DONOR     → React routes /me/donations, /me/campaigns, /me/profile,
                   a donor dashboard, and the donate flow.
       VOLUNTEER → /me/profile and a volunteer dashboard with events to join.
  • Staff / superusers — Django admin + full analytics Dashboard + every
    staff/admin management screen in the frontend.

Permission guards, backend (apps/core/views.py and apps/api/views.py):

  @login_required           any authenticated user
  @api_login_required       like above, but returns JSON 403 instead of the
                            HTML redirect that confuses fetch() clients
  @_staff_required          user.is_staff  (approval workflows: confirm event
                            signup, clear background checks)
  @_admin_required          user.is_superuser (edit/delete donor & volunteer)
  @_superuser_required      user.is_superuser (user management endpoints)

The principle: donor/volunteer self-service writes go through /api/me/* (a user
can only ever touch their own linked record); the staff screens are view +
walk-in creation; editing or removing other people's records is admin-only.

Frontend guards (frontend/src/auth/ProtectedRoute.jsx): `staff` and `superuser`
props gate the corresponding routes in App.jsx. The "/" index is role-aware —
volunteers and donors land on their personal dashboard, staff keep analytics.

user_role(user) reads user.profile.role, with a guard that degrades to role-less
if the table hasn't been migrated yet (so /auth/me/ never 500s during the
runserver-auto-reload-vs-migrate race).

6. WORKFLOW: SELF-SERVICE SIGNUP (DONOR & VOLUNTEER)
--------------------------------------------------------------------------------
1. Public page /register (React pages/Register.jsx) collects:
   role (volunteer | donor), and for donors donor_type (individual | org),
   username, email, password (≥ 6 chars).
2. POST /api/auth/register/  (apps/api/views.py → auth_register)
   • Validates role ∈ UserProfile.Role.
   • 409 if the username is already taken.
   • Creates User (password hashed with set_password), a UserProfile(user, role),
     AND the linked profile record:
         volunteer → Volunteer(background_check_status=PENDING)  ← background
                     check is "submitted but not yet reviewed".
         donor     → Donor(donor_type=…).
   • Logs the new user straight in (login(request, user)) and returns 201.
   Staff/superuser accounts are NOT creatable here — an admin provisions those.
3. The frontend redirects to "/" → the RoleHome index shows the matching
   dashboard (VolunteerDashboard or DonorDashboard).

Staff can also add donors/volunteers manually (POST /api/donors/create/,
/volunteers/create/) — those records have no linked User, so their "owner"
leaves user= NULL and they can't log in to self-service pages.

7. WORKFLOW: ONLINE DONATION VIA RAZORPAY
--------------------------------------------------------------------------------
Everything happens on one screen: the donor picks a campaign, clicks Donate,
enters an amount in the modal, pays inside Razorpay's popup, and is thanked.

1. Donor → "Donate" on a campaign card (DonorDashboard or /me/campaigns).
2. Frontend calls the shared hook hooks/useDonate.js → handleDonate(c, amount):
   a. POST /api/campaigns/<id>/checkout/  (apps/core/views.py → campaign_checkout)
        - role must be DONOR, donor profile must exist (else 403).
        - amount must be > 0 and ≥ ₹1 (Razorpay's minimum is 100 paise).
        - _campaign_goal_guard: won't exceed the campaign's goal (else 400
          with "this campaign needs only ₹X more…").
        - If keys are NOT configured → records an offline donation (see §8).
        - Otherwise creates a Donation row with status INITIATED, then calls
          payments/services.create_razorpay_order(donation), which:
              • amount × 100 → paise
              • razorpay Client.order.create({amount_paise, currency, receipt,
                payment_capture: 1, notes}) → order["id"]
              • saves razorpay_order_id + status "order_created", returns the order.
        - On any gateway error the initiated row is DELETED and a clean JSON
          500 ("Could not start the payment…") is returned — no raw exception.
        - On success returns {mode:"online", donation_id, order_id, key_id,
          amount_paise, currency, name, description, prefill:{name,email,contact}}.
   b. Frontend opens the Razorpay-hosted modal via lib/razorpay.js →
      payWithRazorpay() (injects https://checkout.razorpay.com/v1/checkout.js).
      The donor never enters card details on our site. Promise rejects with
      code "cancelled" if the window is dismissed (silently ignored) or "failed"
      if a payment attempt fails (toasted).
   c. On success the promise resolves with {razorpay_order_id,
      razorpay_payment_id, razorpay_signature}.
3. Frontend → POST /api/donations/verify/  (campaign… donation_verify):
   • Requires donation_id + the three razorpay fields (else 400).
   • donation must exist AND belong to this donor (404 otherwise; order mismatch
     guard if the row already has a different order id).
   • Server-side signature check: payments/services.verify_payment_signature —
     HMAC-SHA256 over "order_id|payment_id" keyed with RAZORPAY_KEY_SECRET,
     compared with hmac.compare_digest. (The client is never trusted alone.)
   • Only on success does the donation become CAPTURED with date=now and the
     three identifiers stored.
4. useDonate toasts "Payment successful! Thank you…" and refreshes the page
   data, so the dashboard shows the new donation and campaign progress.

Why two backend calls (checkout then verify)? Checkout only *creates an order*
and returns the config for the popup; the actual money move is confirmed by the
client callback, and that callback is re-verified cryptographically on the
server before we record captured money. Belt and suspenders: the webhook (§9)
is the independent reconciliation channel.


--------------------------------------------------------------------------------
8. WORKFLOW: OFFLINE / CASH DONATION
--------------------------------------------------------------------------------
When Razorpay keys are ABSENT from .env (no online payments), campaign_checkout
still happily records the gift immediately as an offline/cash donation:

    status = captured, date = now, mode: "offline", donation_id

The frontend (useDonate) sees mode "offline", toasts
"Razorpay isn't configured yet, so this was recorded as an offline/cash
donation" + a pointer to this file, and the money is already captured. This is
deliberate: an "expected fallback" should not paint a red 5xx in the console
during a demo. It also means staff can demo the whole donor flow with zero setup.

There is also the pure offline path: staff record a walk-in donation via
POST /api/donations/create/ (pick donor, campaign, amount; status captured) —
that is a separate staff-capture flow (§9 covers statuses more broadly).

9. WORKFLOW: DONATION STATUSES & RECONCILIATION (RAZORPAY WEBHOOK)
--------------------------------------------------------------------------------
A donation's status mirrors the Razorpay payment lifecycle, stored in
Donation.status (apps/core/models.py):

    initiated            just created server-side, order not yet made
    order_created        Razorpay order created (link sent), awaiting payment
    payment_pending      donor authorized (payment.authorized event / transient)
    captured / succeeded money received — the "good" states for totals
    failed               payment failed (or refused)
    part_refunded        a refund < full amount
    refunded             fully refunded

"Money in" for all totals (donor.total_given, campaign.raised_amount, dashboard
sums, CSV export, PDF statement) is any of:
    captured, succeeded, part_refunded, refunded
i.e. refunds are counted at their (possibly reduced) final amount.

The reconciliation backstop — webhook (apps/payments/views.py + services.py):
  • Endpoint POST /api/payments/razorpay/ is CSRF-exempt but signature-required.
  • Every request must carry X-Razorpay-Signature = base64(hmac-sha256(raw
    body, RAZORPAY_WEBHOOK_SECRET)). Invalid → 403; missing secret → 500.
  • Each event is stored idempotently in RazorpayWebhookEvent keyed on the
    globally-unique event "id". A duplicate delivery just bumps retry_count and
    returns 200 so Razorpay stops re-posting.
  • process_webhook_event dispatches by event type:
        order.paid / payment.captured → donation marked captured, amount
                                        synced from paise, date set, and
                                        acknowledgement triggered (idempotent).
        payment.authorized           → payment_pending
        payment.failed               → failed
        refund.created               → refunded / part_refunded
  • Any processing error marks the event row "failed" but still returns 200 —
    Razorpay stops re-delivering, and the failed rows are the paper trail to
    reconcile by hand or replay.
  • Acknowledgements (FR-4.1): after capture, _trigger_acknowledgement logs the
    ACK and stamps acknowledgement_sent_at (once only). The actual email send is
    a TODO placeholder — wire an email backend/SES/Sendgrid there.

In the current checkout flow the verify endpoint (§7) captures donations
synchronously, so the webhook is redundant-but-reassuring; it becomes the
primary channel for Payment Links and future flows that don't go through the
verified checkout popup.

10. WORKFLOW: CAMPAIGN LIFECYCLE
--------------------------------------------------------------------------------
A campaign is a fundraiser: name + optional slug, description, a goal amount
(0 = "no goal", open-ended), start/end dates, and a status.

  draft       being set up, not yet accepting donations
  active      visible to donors, accepts donations (checked at write time)
  completed   staff closes it after the goal is met / drive ends
  cancelled   abandoned

Lifecycle actions (staff, via the Campaigns screen or Django admin):
  • Create (POST /api/campaigns/create/) — slug auto-generated with a uuid
    suffix on collision; goal coerced to Decimal; validation failures → 400,
    timing races → 409, DB unavailable → 503 (no silent 500s).
  • Update (PATCH) — name, description, status, goal, dates. Clearing goal → 0.
  • Delete (DELETE) — hard delete (donations keep their FK through SET_NULL
    campaign, so history survives).

Money math (all properties, apps/core/models.py):
  • raised_amount   = sum of captured/succeeded/part_refunded/refunded amounts.
  • progress_percent= round(raised / goal × 100, 1); 0 when goal is unset.
  • goal_reached    = (goal > 0 and raised ≥ goal), exposed in the JSON payload.

Goal guard (apps/core/views.py _campaign_goal_guard): whenever a donation is
recorded (online, offline, or staff), if remaining ≤ 0 the campaign refuses new
money; if a single amount would overshoot, the API rejects it with a helpful
"the campaign needs only ₹X more" message. The button turns into a green
"Goal reached ✓" once goal_reached flips (§13), so donors see it live.

Note: campaign status is NOT auto-flipped on goal — staff closes it. The guard
simply stops over-collection.


--------------------------------------------------------------------------------
11. WORKFLOW: VOLUNTEER REGISTRATION & BACKGROUND CHECKS
--------------------------------------------------------------------------------
Volunteers can come in two ways: they self-register (§6) creating a Volunteer
with background_check_status = PENDING, or staff create a Volunteer directly
(often not_required).

Background verification (staff approval workflow):
  • The volunteer's background_check_status starts pending.
  • Staff run it via POST /api/volunteers/<id>/background-verify/ with
    {approved: true|false} → status becomes cleared or rejected.
  • This is deliberately a *staff* action, NOT admin: running a background check
    should not require superuser rights (see _staff_required vs _admin_required
    in §5). General volunteer editing remains admin-only.
  • Rejected volunteers still exist as records (their signups/history stay an
    audit trail); is_active is what actually hides anyone from lists.

Volunteer shifts (admin-managed): VolunteerShift has draft → open → locked →
completed/cancelled stages and a capacity; volunteers sign up per shift
(ShiftSignup, unique per volunteer+shift) and staff check them in/out and log
hours, which roll up into the volunteer's total_hours.

Events are the donor-facing volunteer activity surface — see §12. The volunteer
self-service dashboard is §14.


--------------------------------------------------------------------------------
12. WORKFLOW: EVENTS (PUBLISH, REGISTER, CONFIRM, REVENUE)
--------------------------------------------------------------------------------
An Event is a fundraising event/drive/gathering with a start/end time, location,
capacity (0 = unlimited), ticket_price (0 = free), and an OPTIONAL link to a
Campaign so event revenue flows into that campaign's total (FR-6.3).

Lifecycle:
  draft → published → completed | cancelled
  Only published events appear to volunteers as "upcoming events".

Volunteer self-service (must be a logged-in VOLUNTEER, apps/core/views.py):
  • POST /api/events/<id>/register/  (event_register)
      - volunteer profile required (403 otherwise).
      - 409 if they already have an active (non-cancelled) registration.
      - Status decision:
          capacity reached → WAITLISTED
          free event (ticket ≤ 0) → CONFIRMED (auto-confirms)
          paid event → PENDING (payment is collected offline/at the desk)
      - attendee_name/email are copied from the volunteer.
  • POST /api/events/<id>/cancel/  (event_cancel) — sets their registration to
    CANCELLED. They can re-register later.

Staff approval workflow (the "pending" queue):
  • GET  /api/events/registrations/pending/ — everyone status PENDING or
    WAITLISTED, ordered by event start time (nearest first).
  • POST /api/event-registrations/<id>/confirm/ — marks a signup CONFIRMED.
    (Cancelled registrations refuse re-confirmation.)
  • Revenue counts only confirmed/attended registrations with paid_amount > 0
    (Event.revenue property); registrations_count excludes cancelled.

Events and donations are separate money flows: event revenue is tracked per
registration (paid_amount) and, when the event links to a campaign, is intended
to feed the campaign total — but note it's the *crud* of a campaign-connected
event the revenue aggregates into; donations and event tickets are recorded
independently today.


--------------------------------------------------------------------------------
13. WORKFLOW: DONOR SELF-SERVICE DASHBOARD
--------------------------------------------------------------------------------
Logged-in donors land on DonorDashboard ("/"). Everything here is read-only
except profile edits and donations.

Data source: GET /api/me/summary/ (role-scoped). For a donor it returns their
profile, latest 10 donations, stats (total_given, donations_count,
active_campaigns) and the 8 newest ACTIVE campaigns with progress.

On the page:
  • Page-head shows the donor's avatar+name — clicking the avatar or the name
    (or "Edit profile") navigates to /me/profile (they're <Link>s, made to look
    like plain text).
  • Stat tiles (components/StatCard with a `to` prop = clickable <Link>):
      Total given      → /me/donations
      Donations count  → /me/donations
      Active campaigns → /me/campaigns
      Donor type / company
  • "Active campaigns" card — each campaign shows raised, goal, a progress bar,
    and a "Donate" button (disabled while a payment is in flight, replaced by
    "Goal reached ✓" when full). Donate → DonateModal → useDonate (§7).
  • "My donations" card — the recent table with a "View all →" link.

The three stat links open dedicated pages (all under <ProtectedRoute> so they
need an authenticated session):

  /me/donations  (pages/MyDonations.jsx, GET /api/me/donations/)
      ALL of the donor's transactions (no [:10] cap), newest first; header
      shows the count and lifetime total (donor's total_given); "Export PDF"
      button → lib/exportPdf.js builds a branded A4 PDF (forest-green header,
      autoTable rows # / Date / Campaign / Amount / Status / Receipt, summary
      line, page footers) entirely in the browser via jsPDF — no server round
      trip — and downloads donations-<name>.pdf.
      Non-donors get a JSON 403 from this endpoint (donation data is private).

  /me/campaigns  (pages/MyCampaigns.jsx, GET /api/me/campaigns/)
      EVERY active campaign (no [:8] cap), same cards + DonateModal, shared
      useDonate hook.

  /me/profile     (pages/MyProfile.jsx, PATCH /api/me/profile/)
      Role-aware edit form. Donors edit name, donor_type, email, phone, company,
      source; volunteers edit name, email, phone, skills. Tagging (donors) and
      the background-check decision (volunteers) stay admin-managed on purpose.
      Saving shows a toast and navigates back to the dashboard, which refetches.

PDF generation detail: exportDonationsPdf uses jspdf + jspdf-autotable (npm
deps, imported via `import autoTable from 'jspdf-autotable'`), formats money
with formatINR (lakh-separated ₹), and sanitizes the filename from the donor's
name. Works fully offline once the bundle is loaded.

Shared hooks worth knowing:
  • useData(urlOrFn, deps) → {data, loading, error, refresh} — every page's
    data fetching.
  • useDonate({refresh}) → {paying, donateFor, setDonateFor, handleDonate} —
    the whole checkout → modal → verify → toast → refresh dance, so the donor
    dashboard and MyCampaigns never duplicate it (§7).
  • useClientFilter(sourceArray, fields) → query + setQuery + filtered — the
    client-side search boxes (e.g. the Donations list).
  • useAuth() — the session (user object incl. role) and login/logout/register.


--------------------------------------------------------------------------------
14. WORKFLOW: VOLUNTEER SELF-SERVICE DASHBOARD
--------------------------------------------------------------------------------
Logged-in volunteers land on VolunteerDashboard ("/"), fed by the same
GET /api/me/summary/ (the volunteer branch): profile, stats (active
registrations, upcoming events, total hours), their own registrations, and the
8 next PUBLISHED events (within the next 6h window).

  • Page-head = avatar+name (clickable → /me/profile) + "Edit profile" button.
  • Stats: active registrations, upcoming events, hours logged, background-check
    status (or skills).
  • "My registrations" table: event, start time, StatusBadge, ticket price, and
    a Cancel button (hidden once cancelled). Cancel posts event_cancel and
    refreshes.
  • "Upcoming events" grid: date chip (day + month), name/time, location, price,
    and a Register button — or "Registered ✓" if already in. Register posts
    event_register and refreshes; the server's capacity/free/paid rules (§12)
    decide confirmed vs pending vs waitlist, surfaced back via the badge.

Volunteers edit their own profile on /me/profile exactly like donors (§13).


--------------------------------------------------------------------------------
15. WORKFLOW: STAFF ANALYTICS DASHBOARD & CSV EXPORT
--------------------------------------------------------------------------------
Staff/superusers get the full analytics Dashboard at "/" (pages/Dashboard.jsx):

  Data: GET /api/dashboard/ (apps/reports/views.py → services)
    donations  total + count of money-in donations
    trend      last 6 months of captured donations, oldest-first; empty months
               appear with zero so the axis is complete (Python bucketing so the
               query is identical on SQLite and Postgres)
    recent_donations  the 8 latest (donor, campaign, amount, status, date)
    campaigns  per-campaign raised vs goal + progress
    volunteers active count, hours logged, upcoming open shifts

  Rendering: four StatCards (total raised, active campaigns, volunteers,
  hours logged), a Chart.js bar chart of donations per month (theme colors read
  live from CSS variables, INR tooltips, "k" y-axis labels), campaign progress
  list with links into each campaign, and a recent-donations table. The chart's
  data is also available as a plain <table> in a <details> ("Data table") for
  accessibility. All tables sit in .table-wrap so long content scrolls on small
  screens.

  Campaign detail (/campaigns/:id): progress ring (SVG), raised-vs-goal, the
  description, start/end, and every donation against it.

CSV export (FR-5.2): GET /api/reports/monthly-donations.csv?year=YYYY&month=MM
downloads month-donations with columns donor, email, campaign, amount, currency,
status, date, receipt — money-in statuses only. Fine at NGO scale (hundreds of
rows); the comment flags streaming as the upgrade path past ~10k rows.

Scheduled reports: the services are pure DB aggregations; schedule a management
command or a URL fetch (see README) — no cron lives in the code yet.

Django admin (/admin) remains the full-power home for staff editing anything,
including data the self-service screens intentionally leave readonly (tags,
background-check decisions, user management).

16. WORKFLOW: DONOR DEDUPLICATION & MERGE
--------------------------------------------------------------------------------
apps/core/services.py:

  find_duplicate_donors() — a naive detector O(n): keys active donors by
  lowercased email, falling back to the (lowercased name, phone) pair; anyone
  colliding with an earlier key is flagged as {survivor, duplicate}. Returned
  pairs feed a merge UI.

  merge_donors(survivor, *losers, audit_notes) — FR-1.3. In ONE atomic
  transaction (transaction.atomic):
      • every donation and communication of each loser is re-pointed at the
        survivor (FK rewrite).
      • each loser is soft-deleted: is_active=False, merged_into=survivor, and
        an audit note appended ("Merged into #<pk> ...") so the record and its
        history survive for FK PROTECT + audit.
  Donor records are never hard-deleted for the same reason (donor_delete is a
  soft delete too) — a donor row keeps donation history addressable forever.

  donor_timeline(donor) — a chronological merge of that donor's communications
  and donations, shown on the donor detail page (GET /api/donors/<id>). Each
  timeline item is {at, kind (communication|donation), detail}.

  successful_donation_amount_sum(donor) — simple Sum of all donations (used by
  the receipts/analytics helpers); note total_given (models property) filters to
  money-in statuses, so prefer the property for "what actually counts".

app works from a narrow phone up to a wide desktop without layout breakage:

20. KNOWN GOTCHAS & TIPS
--------------------------------------------------------------------------------
1. Apps import as top-level packages (§3). Never write `from apps.core.models
   import …` — it breaks the app registry with a confusing error.
2. Razorpay keys blank → payments silently become offline/cash (§8). That's
   intended for demos, but check `.env` before wondering why nothing hits the
   gateway.
3. NODE_ENV=production on this machine makes `npm install` skip devDependencies
   (no `vite`), producing "vite not recognized". Fix: `npm install --include=dev`.
4. Razorpay amounts are paise only at the boundary. Store and display INR
   (Decimal); convert with int(round(amount * 100)).
5. Vite stale-module errors (e.g. "Failed to resolve import ./pages/MyCampaigns
   .jsx" with old line numbers, even though the file exists) are a stale dev
   server. Restart `npm run dev` (or clear node_modules/.vite).
6. Login/CSRF: one login covers both the React app and the Django admin
   (shared session). Any non-GET fetch must send X-CSRFToken (§3).
7. money-in statuses captured/succeeded/part_refunded/refunded are what every
   "total" is computed from (§9). Don't add raw initiated rows to totals.
8. The live database is Supabase/Postgres; SQLite was a migration staging store
   and is no longer used (see .env's DJANGO_DB_*).
9. .env and db.sqlite3 are gitignored. Never commit secrets (Razorpay keys,
   DB password, DJANGO_SECRET_KEY) — .env.example holds variable names only.
